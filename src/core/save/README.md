# core/save

**Owner:** WP5 (game loop). **Status:** implemented. API: `checksumState`, `saveMetaFor`, `createSave`, `serializeSave`, `parseSave`, `validateState`, `MIGRATIONS` (contract; state schema v5) plus `parseSaveWith` (explicit migration list, for tests) and `GameStateSchema`.

## parseSave order and error codes
1. `JSON.parse` → `save.json`
2. `format` tag, malformed envelope → `save.format`
3. `schemaVersion` newer than the build → `save.too-new` (details: saveVersion, buildVersion)
4. checksum of the state as written, by the rule of the save's schema version → `save.checksum`. v1: `hashString(stableStringify(state))`. v2: an order-sensitive `StreamHasher` over each top-level key and its JSON text, with `results`, `history` and `alumni` folded in per entry (key, then the entry's `hashString`) (`encode.ts`)
5. stepwise migrations vN → vN+1 (missing or throwing step) → `save.migration`
6. structure: strict zod schema of the whole `GameState` → `save.structure`
7. content: another theme, or any referenced content id missing → `save.content-missing`; a different content hash with every id present loads with a warning
8. references and the ledger invariant (balance = opening + Σ entries) → `save.references`

`save.storage` belongs to `src/platform`. A failed parse never returns a state.

## validateState
Structure (strict: an unknown key is an error, so a module writing an undeclared field is caught by the soak), content ids (classes, races, traits, presets, tiers, regions, districts, AI personalities, paces, stats, weeks, venues), and references: map keys equal ids, clubs/fighters/fixtures/competitions resolve, lineup fighters on the roster (hired blades allowed), captain ≠ vice, contract club = fighter club, status consistency, fixture `played` ⇔ result, offers only to free agents, ledger sequence and the balance invariant, id counters ahead of every allocated id, calendar consistent with `leagues.json`. Issues are capped at 200 per group.

## Decisions
- `serializeSave` output equals `JSON.stringify(envelope)`. Results, archived seasons and alumni are deep-frozen once a transition shares them, so their JSON text and hash are cached per entry object; an autosave encodes only the mutable part of the state.
- The v2 checksum depends on key order. JSON.parse keeps it, so a parsed save hashes the same; states built by the engine are deterministic in key order too.
- **v1 → v2** (`migrations.ts`): retired fighters and past hired blades move to `alumni`, and every shortlist, lineup, offer and negotiation entry naming them is dropped; agreed renewals move from negotiations to `Contract.next`; `FreeAgency.enteredAt`, `Injury.careerEnding` and `TierSeasonRecord.reckoningStages` (from the clubs' season rows) are filled in; fighter history rows keep display stats on the last two rows only.
- After a migration the envelope carries the checksum of the migrated state and `migratedFrom`.
- Array lengths and counters that content values feed into (squad size, reserves, swaps per match, queued level-ups, options per level-up, perks per fighter) are built from `SAVE_BOUNDS` (`core/content/save-bounds.ts`), the same constants `core/content/validate.ts` checks the content against, so tuning a content value past the schema is refused at content load instead of producing a save that cannot be loaded.
- `MatchResult.fighterTotals` (optional tuple per fighter, written by league compaction only) is an additive field of schema v3: saves without it load unchanged.
- **v3 -> v4 (KI-2, identity).** In-season compaction (core/league `compactAgedResults`, `leagues.json matchRecords.compactAiMatchesAfterWeeks`) writes the same compacted shape the season-end rule already did, plus one more optional field, `MatchResult.fielded` (each side's round-1 five as `[fighter id, row 0/1, kickoff rating]`, so the renewal ask and the opponent's last lineup keep reading what they read). No existing data changes, so `migrateV3ToV4` returns the state as it is and the runner stamps `schemaVersion` 4. The bump is for older builds: a save holding `fielded` made main's strict schema answer "the save is damaged: its structure is invalid" (`save.structure`, Unrecognized key), while a version past the build's own is reported as `save.too-new` (save version 4, build 3). Every v3 save (the owner's R001 and R002 careers, ticket reproductions, a real v3 save written by main in `tests/fixtures/saves/ki2-v3-main-s2w7.json.gz`) loads: `migratedFrom` is 3, its full results are compacted by the week rule from its next week on, and a previous season compacted by an older build simply has no `fielded` (nothing reads last season's fives). Loading a v3 save and saving it again writes v4, which older builds will refuse as too new. `tests/save/compaction-saves.test.ts` and `save.test.ts` cover the round trip, the v3 step, the R001 careers and the report of a compacted match.
- **v4 -> v5 (M2 arena viewer, identity; docs/design/_drafts/05-technical-m2.md §A3, tech-023).** Three optional fields join the strict schema: `MatchState.watch` (`LiveWatch`: `mode` 'watch' | 'simulate', `round` (the round waiting to be watched, or null), `cursorTick` (the reveal frontier, a fight tick), `calls` (RESERVED, at most `SAVE_BOUNDS.callsPerRound`)), `RoundLineups.calls` (RESERVED call plans: `none`, `policy` or `explicit` with at most `callsPerRound` calls) and `MatchResult.simHash` (the sim content hash, for replay availability). A v4 state holds none of them, so `migrateV4ToV5` returns it as it is and the runner stamps 5: a v4 live match is a simulated match and v4 results fall back to their content hash for replays. The bump is for older builds: a v4 build refuses a v5 save as `save.too-new` (save 5, build 4) instead of calling it damaged. References (`validate.ts`): a watched round only in mode 'watch' and only as the pending round (`rounds + 1` in phase `round_pending`, and a watched match in that phase always names it), a cursor within the round time cap. `save.test.ts` covers the v4 round trip (a live match included: loads as v5 with nothing but the version stamped, saves back to the same bytes) and the new fields' bounds; `npx tsx scripts/replay.ts <save> --watch` loads a real save (the owner's R002-T006 ticket, v3) through v4 and v5, saves it back identically and plays weeks watched and simulated.
- `STATE_SCHEMA_VERSION` (5) and the call-count bound of `SAVE_BOUNDS` were set by WP-M2B under the architect's exceptions (05-technical-m2 §A13).
- The schema mirrors `core/model`; a model change bumps `STATE_SCHEMA_VERSION`, adds a migration and updates `schema.ts` together (architect).

## Orchestrator decisions (M1 core fix round, pending owner confirmation)
- **Tampered-save ids.** Names every plain object inherits (`constructor`, `toString`, `hasOwnProperty`, `__proto__`, ...) are never valid: `reservedNameIssues` rejects them anywhere in the state as a map key, as a value under `id` / `...Id` / `captainAtLastLock`, and as any string in an array (id lists, shortlists, seeds), before the zod check (`save.structure`). Reference checks look ids up in null-prototype copies. A save with `playerClubId: "constructor"` no longer loads.
